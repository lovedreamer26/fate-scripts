# Диагностический обмен Bridge

## Сессия GM

В приложении откройте «Foundry — сессия GM», укажите Origin и ID мира. Сгенерированный код действителен две минуты. В настройках Foundry нажмите «Fate Scripts — сопряжение GM» и подтвердите разрешение на запуск сохранённых скриптов в этом мире. После подтверждения одноразовый код заменяется новым токеном, который хранится в sessionStorage вкладки GM. Каждый запрос идёт на локальный порт с Bearer и привязкой Origin, мира, ID GM и профиля Foundry. Через восемь часов или при отзыве потребуется новый код. Перезапуск самого Fate Scripts также завершает сессию.

POST /fate-scripts/session/v1 обрабатывает `pair`, `poll`, `authorize_write`, `report` и `revoke`. Опрос после сетевой ошибки возобновляет соединение. Работа выдаётся один раз после записи ID в SQLite. Просроченный запуск, уже переданный Foundry, получает статус `unknown`. Отзыв не останавливает JavaScript, который уже начал выполняться. В режиме записи мастер видит подтверждение с исходным и новым кодом. После его согласия Bridge запрашивает одноразовое разрешение на запись для этого ID. Просроченный или отозванный запрос не получит разрешение.

Закреплённый идентификатор соответствует профилю Foundry на выбранном Origin. Для смены браузерного профиля сначала отзовите сессию и явно забудьте старый идентификатор. Защита рассчитана на локальный хост и доверенный клиент GM. Сторонние модули, загруженные в тот же origin, имеют доступ к его клиентскому контексту.

Для достоверной привязки логов используйте `scope.fateScriptsConsole?.log(...)` либо соответствующий `warn` или `error`. Обычный глобальный console остаётся доступен в Foundry. Данные неизвестных объектов не сериализуются. Статус `returned` означает возврат из execute.

Тестовый процесс запускает HTTP-сервер на 127.0.0.1 и случайном свободном порту. Привязка к точному Foundry Origin настраивается при запуске. Одноразовый 256-битный ключ живёт в памяти процесса. GM явно вводит код в локальный диалог. Клиент отправляет POST на /fate-scripts/probe/v1 с JSON и Bearer. Сервер допускает один успешно проверенный запрос, контролирует Origin и ограничивает тело 4096 байтами. Клиент подтверждает только HTTP 204.

Диагностика передаёт версию и количества объектов. Права проверяются клиентским Foundry. Origin служит дополнительной проверкой браузерного запроса. GM и загруженные модули обладают доступом к клиентскому контексту. Локальное ПО и содержимое той же страницы входят в модель угроз будущего транспорта.

Релизный двунаправленный протокол ещё не реализован. Критерии для него включают взаимную аутентификацию, отзыв сессии, единоразовое применение команд, проверку server/world/user и отсутствие публичного JS endpoint.

## Идентичность мира в Bridge 0.2.2

GM при первом явном сопряжении создаёт UUID в скрытой настройке мира worldIdentity. Значение не является секретом. Настольное приложение закрепляет пару Origin и ID мира за этим UUID в SQLite v8. UUID сохраняется при смене профиля и перезапуске Foundry, пока сохранена база мира. Разные миры на одном Origin закрепляются отдельно. Идентичность не является уникальным номером физической установки: полная копия мира с тем же Origin и ID сохраняет тот же UUID. При переносе или смене адреса автоматического объединения нет.

Старую привязку из SQLite v6/v7 можно расширить новым UUID, предъявив прежний ID профиля при первом сопряжении на 0.2.2. Если предыдущий профиль недоступен, GM после проверки адреса может явно забыть прежние привязки через интерфейс. Старый модуль без identityKind world-v1 отвергается. Срок действия и повторное подтверждение полномочий не меняются.
